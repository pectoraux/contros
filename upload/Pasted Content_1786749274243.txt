## What Z.ai actually got right

There is real substance here.

The schema explicitly declares PostgreSQL, and the domain model includes organizations, users, opportunities, work definitions, estimates, bids and audit logs. ([GitHub][2])

The estimate API exposes Work Definition versions, cost recipes, productivity, hazards, controls, provenance and revisions, which is directionally consistent with our architecture. ([GitHub][3])

The pricing engine is deterministic and records provenance rather than asking the LLM to produce arbitrary prices. ([GitHub][4])

The pre-submission gate also exists as a deterministic engine and checks scope completeness, assumptions, unpriced lines, unsourced rates, subcontract coverage, deliverables and commercial approval. ([GitHub][5])

The repo also has a real separation between the UI and `src/lib/engines`, which is a good foundation. ([GitHub][6])

So I would **not throw this away**.

But there are serious problems.

# P0 — The API is currently not enforcing tenant isolation

This is the biggest issue I found.

The database schema has `organizationId` on the major records and the auth implementation puts `organizationId` into the NextAuth JWT/session. ([GitHub][2])

But the actual API routes are not consistently using that authenticated identity to scope queries.

For example, the dashboard route simply does:

```ts
db.opportunity.count(...)
db.subcontractPackage.count(...)
db.estimate.count(...)
db.knowledgeAlert.count(...)
db.auditLog.findMany(...)
db.opportunity.groupBy(...)
```

with **no organization filter**. ([GitHub][7])

The opportunities list likewise calls:

```ts
db.opportunity.findMany(...)
```

without an organization constraint. ([GitHub][8])

That's incompatible with the architecture we froze:

> Every organization must be isolated from every other organization.

Having `organizationId` in the schema is not enough.

### Required fix

Create one mandatory server-side auth/context function, something like:

```ts
requireAuth()
requireOrganization()
requireRole()
```

and make every API route obtain:

```ts
const ctx = await requireRequestContext()

ctx.userId
ctx.organizationId
ctx.role
```

Then every query must be scoped through server-derived `ctx.organizationId`.

Even better, centralize repositories so application code cannot accidentally issue an unscoped query.

For example:

```ts
opportunityRepository.list(ctx, ...)
```

rather than:

```ts
db.opportunity.findMany(...)
```

throughout the app.

### Do not allow this pattern

```ts
where: { id }
```

for organization-owned entities.

It must be:

```ts
where: {
  id,
  organizationId: ctx.organizationId
}
```

or, preferably, enforced at a repository/service boundary.

# P0 — The estimator can currently produce materially wrong costs

This is more serious than a normal MVP approximation.

The pricing engine explicitly says:

> Missing price observation → unsourced, line contributes 0. ([GitHub][4])

That means:

```text
Cement
GHS 45
Sand
GHS 30
Labour
MISSING
```

can produce a direct cost that silently excludes labour.

The UI later flags the line as unsourced, but **the mathematical estimate is already wrong**.

Our invariant was not:

> "Flag bad estimates."

It was:

> **"Never let an unsupported number silently become the commercial truth."**

### Correct behavior

A missing mandatory price should produce:

```text
calculationStatus = incomplete
```

not:

```text
cost contribution = 0
```

The engine should return something like:

```ts
{
  status: "incomplete",
  blockingInputs: [
    {
      kind: "missing-price",
      resourceId,
      resourceName
    }
  ]
}
```

and should not produce a commit-ready `sellPrice`.

The UI can still show a provisional estimate, but it must be explicitly provisional.

# P0 — The hybrid subcontracting logic is an unacceptable heuristic

This is probably the most concerning piece of the actual pricing engine.

Z.ai has:

```ts
// Heuristic: 50% of equivalent self-perform cost is subcontracted.
subcontractCost = subcontractFromRecipe + selfPerformTotal * 0.5;
```

and:

```ts
// The quote (if any) is ignored under this heuristic.
```

([GitHub][4])

That cannot exist in the commercial engine.

We explicitly designed:

```text
Self-perform
Subcontract
Hybrid
```

as **real execution strategies**, not arbitrary assumptions.

A 50/50 heuristic can materially distort a bid.

### Required model

Hybrid must define the actual split.

For example:

```text
WorkPackage
 ├── selfPerformComponents
 └── subcontractComponents
```

or:

```text
EstimateLine
 ├── executionSegments[]
 │     ├── strategy
 │     ├── scope
 │     ├── quantity
 │     └── cost basis
```

Then:

```text
70% self-perform
30% subcontract
```

must actually mean 70/30, based on a structured allocation.

If there is no allocation:

> **The estimate is incomplete.**

Never invent 50%.

# P0 — The current "margin" is wrong

This is subtle but important.

The pricing engine calculates:

```ts
marginPct = (sellPrice - projectCost) / sellPrice
```

where `projectCost = directCost`. ([GitHub][4])

But the actual sell price already includes:

```text
risk
overhead
profit
```

So this metric is not the actual profit margin.

The API also exposes:

```ts
averageMarginPct = (totalSell - totalDirect) / totalSell
```

which has the same conceptual problem. ([GitHub][3])

We need at least distinguish:

```text
gross margin
contribution margin
operating margin
target profit margin
```

For this MVP, the simplest correct model is:

```text
direct cost
+ project overhead
+ contingency/risk
= estimated total cost

sell price
- estimated total cost
= expected profit

expected profit / sell price
= expected margin
```

The UI must not label a cost-to-sell spread as "margin" if it includes no overhead/risk treatment.

# P0 — The subcontract reconciliation algorithm is far too weak

This is the biggest domain-model problem after pricing.

The current matching algorithm is literally bidirectional substring matching:

```ts
la.includes(lb) || lb.includes(la)
```

and then matches the first unused quote line. ([GitHub][10])

That is not sufficient for real subcontract packages.

Example:

```text Required:
Supply and install aluminum windows, 1,000m²

Sub quote:
Aluminium windows
Supply only
```

A textual match can report coverage even though **installation is absent**.

Worse, if a subcontractor sends a lump-sum quote without line detail, the implementation says:

> treat whole quote.totalAmount as coverage. ([GitHub][10])

That defeats the entire purpose of scope reconciliation.

### Correct architecture

Reconciliation should be based on **scope atoms**, not descriptions.

Example:

```text
Package:
Aluminium windows

Required scope atoms:
  manufacture
  delivery
  installation
  sealant
  scaffolding
  testing
  finishing

Sub quote:
  manufacture ✓
  delivery ✓
  installation ✗
  sealant ✗
  scaffolding ✗
```

Then coverage becomes semantic and auditable.

AI can assist with mapping quote language to scope atoms, but the mapping must enter structured data and be reviewable.

# 2. P0 — TENANT ISOLATION AND AUTHORIZATION

This is the highest priority.

The current schema contains `organizationId` and NextAuth puts `organizationId` into the session/JWT, which is good.

However, several API routes currently query organization-owned tables without organization scoping.

For example, the dashboard currently performs unscoped queries over opportunities, subcontract packages, estimates, knowledge alerts and audit logs.

The opportunities API also performs an unscoped `Opportunity.findMany`.

This violates the invariant:

> Every organization must be isolated from every other organization.

## Required implementation

Create a mandatory request context abstraction:

```ts
interface RequestContext {
  userId: string
  organizationId: string
  role: 'estimator' | 'manager' | 'director' | 'admin'
  isDemo: boolean
}
```

Create functions along the lines of:

```ts
requireAuth()
requireRole(...)
```

The exact names may follow project conventions.

Every protected API route MUST obtain the server-side context.

Never trust:

```text
organizationId
userId
role
```

from the request body or query string.

## Repository rule

Every query involving organization-owned data must be organization-scoped.

Bad:

```ts
db.opportunity.findUnique({
  where: { id }
})
```

Good:

```ts
db.opportunity.findFirst({
  where: {
    id,
    organizationId: ctx.organizationId
  }
})
```

For updates/deletes, require the same compound scope.

Prefer a repository/service layer so developers cannot accidentally issue unscoped queries.

## Add security tests

Create at least these tests:

```text
User from Org A cannot GET Org B opportunity
User from Org A cannot GET Org B estimate
User from Org A cannot GET Org B work definition
User from Org A cannot GET Org B subcontract quote
User from Org A cannot modify Org B estimate
User from Org A cannot modify Org B work definition
User from Org A cannot see Org B audit logs
User from Org A cannot access Org B AI context
```

These tests are P0.

Do not proceed until they pass.

# 7. P0 — REBUILD SUBCONTRACT SCOPE RECONCILIATION

The current algorithm uses simple bidirectional substring matching and, when quote line detail is absent, treats the entire quote amount as scope coverage.

That is insufficient.

We explicitly designed subcontract reconciliation as a commercial protection mechanism.

Do not fake semantic coverage with string matching.

## New model

Represent required scope as structured scope atoms.

Example:

```text
Aluminium Windows Package

  manufacturing
  delivery
  installation
  sealant
  scaffolding
  finishing
```

```text

sealant            excluded
scaffolding        unknown
finishing          covered

```

Coverage must be calculated from these structured assignments.

AI may propose a mapping from supplier language to required scope atoms.

Never treat:

```text

```

as:

```text

```

unless an explicit user or verified document analysis establishes that coverage.

A lump-sum quote with no scope detail should be:

```text
scopeCoverageStatus = unknown
```

and should trigger review.

## Required result

For every selected subcontract quote show:

```text

covered scope
excluded scope
unstated scope
assumptions
commercial exposure
```

```text
overlapping quote lines
duplicate quote lines
```

Two organizations cannot read or mutate one another's data.

### Pricing correctness

Missing evidence cannot silently become zero cost.

### Hybrid strategy

No arbitrary 50/50 pricing exists anywhere.

### Margin

Displayed margin reflects actual estimated total cost.

### Subcontracting

Scope coverage is based on structured scope, not substring heuristics.

### Reproducibility

A finalized estimate can be reconstructed exactly.

### Exceptions

All commercial overrides are auditable.

### AI

AI cannot directly commit an unsourced commercial value.

### Database

Neon PostgreSQL is the only canonical persistence layer.

### Tests

The above behaviors are covered by automated tests.
