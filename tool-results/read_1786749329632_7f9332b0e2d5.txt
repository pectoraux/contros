    29→# P0 — The API is currently not enforcing tenant isolation
    30→
    31→This is the biggest issue I found.
    32→
    33→The database schema has `organizationId` on the major records and the auth implementation puts `organizationId` into the NextAuth JWT/session. ([GitHub][2])
    34→
    35→But the actual API routes are not consistently using that authenticated identity to scope queries.
    36→
    37→For example, the dashboard route simply does:
    38→
    39→```ts
    40→db.opportunity.count(...)
    41→db.subcontractPackage.count(...)
    42→db.estimate.count(...)
    43→db.knowledgeAlert.count(...)
    44→db.auditLog.findMany(...)
    45→db.opportunity.groupBy(...)
    46→```
    47→
    48→with **no organization filter**. ([GitHub][7])
    49→
    50→The opportunities list likewise calls:
    51→
    52→```ts
    53→db.opportunity.findMany(...)
    54→```
    55→
    56→without an organization constraint. ([GitHub][8])
    57→
    58→That's incompatible with the architecture we froze:
    59→
    60→> Every organization must be isolated from every other organization.
    61→
    62→Having `organizationId` in the schema is not enough.
    63→
    64→### Required fix
    65→
    66→Create one mandatory server-side auth/context function, something like:
    67→
    68→```ts
    69→requireAuth()
    70→requireOrganization()
    71→requireRole()
    72→```
    73→
    74→and make every API route obtain:
    75→
    76→```ts
    77→const ctx = await requireRequestContext()
    78→
    79→ctx.userId
    80→ctx.organizationId
    81→ctx.role
    82→```
    83→
    84→Then every query must be scoped through server-derived `ctx.organizationId`.
    85→
    86→Even better, centralize repositories so application code cannot accidentally issue an unscoped query.
    87→
    88→For example:
    89→
    90→```ts
    91→opportunityRepository.list(ctx, ...)
    92→```
    93→
    94→rather than:
    95→
    96→```ts
    97→db.opportunity.findMany(...)
    98→```
    99→
   100→throughout the app.
   101→
   102→### Do not allow this pattern
   103→
   104→```ts
   105→where: { id }
   106→```
   107→
   108→for organization-owned entities.
   109→
   110→It must be:
   111→
   112→```ts
   113→where: {
   114→  id,
   115→  organizationId: ctx.organizationId
   116→}
   117→```
   118→
   119→or, preferably, enforced at a repository/service boundary.

   164→# P0 — The estimator can currently produce materially wrong costs
   165→
   166→This is more serious than a normal MVP approximation.
   167→
   168→The pricing engine explicitly says:
   169→
   170→> Missing price observation → unsourced, line contributes 0. ([GitHub][4])
   171→
   172→That means:
   173→
   174→```text
   175→Cement
   176→GHS 45
   177→Sand
   178→GHS 30
   179→Labour
   180→MISSING
   181→```
   182→
   183→can produce a direct cost that silently excludes labour.
   184→
   185→The UI later flags the line as unsourced, but **the mathematical estimate is already wrong**.
   186→
   187→Our invariant was not:
   188→
   189→> "Flag bad estimates."
   190→
   191→It was:
   192→
   193→> **"Never let an unsupported number silently become the commercial truth."**
   194→
   195→### Correct behavior
   196→
   197→A missing mandatory price should produce:
   198→
   199→```text
   200→calculationStatus = incomplete
   201→```
   202→
   203→not:
   204→
   205→```text
   206→cost contribution = 0
   207→```
   208→
   209→The engine should return something like:
   210→
   211→```ts
   212→{
   213→  status: "incomplete",
   214→  blockingInputs: [
   215→    {
   216→      kind: "missing-price",
   217→      resourceId,
   218→      resourceName
   219→    }
   220→  ]
   221→}
   222→```
   223→
   224→and should not produce a commit-ready `sellPrice`.
   225→
   226→The UI can still show a provisional estimate, but it must be explicitly provisional.

   230→# P0 — The hybrid subcontracting logic is an unacceptable heuristic
   231→
   232→This is probably the most concerning piece of the actual pricing engine.
   233→
   234→Z.ai has:
   235→
   236→```ts
   237→// Heuristic: 50% of equivalent self-perform cost is subcontracted.
   238→subcontractCost = subcontractFromRecipe + selfPerformTotal * 0.5;
   239→```
   240→
   241→and:
   242→
   243→```ts
   244→// The quote (if any) is ignored under this heuristic.
   245→```
   246→
   247→([GitHub][4])
   248→
   249→That cannot exist in the commercial engine.
   250→
   251→We explicitly designed:
   252→
   253→```text
   254→Self-perform
   255→Subcontract
   256→Hybrid
   257→```
   258→
   259→as **real execution strategies**, not arbitrary assumptions.
   260→
   261→A 50/50 heuristic can materially distort a bid.
   262→
   263→### Required model
   264→
   265→Hybrid must define the actual split.
   266→
   267→For example:
   268→
   269→```text
   270→WorkPackage
   271→ ├── selfPerformComponents
   272→ └── subcontractComponents
   273→```
   274→
   275→or:
   276→
   277→```text
   278→EstimateLine
   279→ ├── executionSegments[]
   280→ │     ├── strategy
   281→ │     ├── scope
   282→ │     ├── quantity
   283→ │     └── cost basis
   284→```
   285→
   286→Then:
   287→
   288→```text
   289→70% self-perform
   290→30% subcontract
   291→```
   292→
   293→must actually mean 70/30, based on a structured allocation.
   294→
   295→If there is no allocation:
   296→
   297→> **The estimate is incomplete.**
   298→
   299→Never invent 50%.

   303→# P0 — The current "margin" is wrong
   304→
   305→This is subtle but important.
   306→
   307→The pricing engine calculates:
   308→
   309→```ts
   310→marginPct = (sellPrice - projectCost) / sellPrice
   311→```
   312→
   313→where `projectCost = directCost`. ([GitHub][4])
   314→
   315→But the actual sell price already includes:
   316→
   317→```text
   318→risk
   319→overhead
   320→profit
   321→```
   322→
   323→So this metric is not the actual profit margin.
   324→
   325→The API also exposes:
   326→
   327→```ts
   328→averageMarginPct = (totalSell - totalDirect) / totalSell
   329→```
   330→
   331→which has the same conceptual problem. ([GitHub][3])
   332→
   333→We need at least distinguish:
   334→
   335→```text
   336→gross margin
   337→contribution margin
   338→operating margin
   339→target profit margin
   340→```
   341→
   342→For this MVP, the simplest correct model is:
   343→
   344→```text
   345→direct cost
   346→+ project overhead
   347→+ contingency/risk
   348→= estimated total cost
   349→
   350→sell price
   351→- estimated total cost
   352→= expected profit
   353→
   354→expected profit / sell price
   355→= expected margin
   356→```
   357→
   358→The UI must not label a cost-to-sell spread as "margin" if it includes no overhead/risk treatment.
   359→

   362→# P0 — The subcontract reconciliation algorithm is far too weak
   363→
   364→This is the biggest domain-model problem after pricing.
   365→
   366→The current matching algorithm is literally bidirectional substring matching:
   367→
   368→```ts
   369→la.includes(lb) || lb.includes(la)
   370→```
   371→
   372→and then matches the first unused quote line. ([GitHub][10])
   373→
   374→That is not sufficient for real subcontract packages.
   375→
   376→Example:
   377→
   378→```text Required:
   379→Supply and install aluminum windows, 1,000m²
   380→
   381→Sub quote:
   382→Aluminium windows
   383→Supply only
   384→```
   385→
   386→A textual match can report coverage even though **installation is absent**.
   387→
   388→Worse, if a subcontractor sends a lump-sum quote without line detail, the implementation says:
   389→
   390→> treat whole quote.totalAmount as coverage. ([GitHub][10])
   391→
   392→That defeats the entire purpose of scope reconciliation.
   393→
   394→### Correct architecture
   395→
   396→Reconciliation should be based on **scope atoms**, not descriptions.
   397→
   398→Example:
   399→
   400→```text
   401→Package:
   402→Aluminium windows
   403→
   404→Required scope atoms:
   405→  manufacture
   406→  delivery
   407→  installation
   408→  sealant
   409→  scaffolding
   410→  testing
   411→  finishing
   412→
   413→Sub quote:
   414→  manufacture ✓
   415→  delivery ✓
   416→  installation ✗
   417→  sealant ✗
   418→  scaffolding ✗
   419→```
   420→
   421→Then coverage becomes semantic and auditable.
   422→
   423→AI can assist with mapping quote language to scope atoms, but the mapping must enter structured data and be reviewable.
   424→

   455→

   729→# 2. P0 — TENANT ISOLATION AND AUTHORIZATION
   730→
   731→This is the highest priority.
   732→
   733→The current schema contains `organizationId` and NextAuth puts `organizationId` into the session/JWT, which is good.
   734→
   735→However, several API routes currently query organization-owned tables without organization scoping.
   736→
   737→For example, the dashboard currently performs unscoped queries over opportunities, subcontract packages, estimates, knowledge alerts and audit logs.
   738→
   739→The opportunities API also performs an unscoped `Opportunity.findMany`.
   740→
   741→This violates the invariant:
   742→
   743→> Every organization must be isolated from every other organization.
   744→
   745→## Required implementation
   746→
   747→Create a mandatory request context abstraction:
   748→
   749→```ts
   750→interface RequestContext {
   751→  userId: string
   752→  organizationId: string
   753→  role: 'estimator' | 'manager' | 'director' | 'admin'
   754→  isDemo: boolean
   755→}
   756→```
   757→
   758→Create functions along the lines of:
   759→
   760→```ts
   761→requireAuth()
   762→requireRole(...)
   763→```
   764→
   765→The exact names may follow project conventions.
   766→
   767→Every protected API route MUST obtain the server-side context.
   768→
   769→Never trust:
   770→
   771→```text
   772→organizationId
   773→userId
   774→role
   775→```
   776→
   777→from the request body or query string.
   778→
   779→## Repository rule
   780→
   781→Every query involving organization-owned data must be organization-scoped.
   782→
   783→Bad:
   784→
   785→```ts
   786→db.opportunity.findUnique({
   787→  where: { id }
   788→})
   789→```
   790→
   791→Good:
   792→
   793→```ts
   794→db.opportunity.findFirst({
   795→  where: {
   796→    id,
   797→    organizationId: ctx.organizationId
   798→  }
   799→})
   800→```
   801→
   802→For updates/deletes, require the same compound scope.
   803→
   804→Prefer a repository/service layer so developers cannot accidentally issue unscoped queries.
   805→
   806→## Add security tests
   807→
   808→Create at least these tests:
   809→
   810→```text
   811→User from Org A cannot GET Org B opportunity
   812→User from Org A cannot GET Org B estimate
   813→User from Org A cannot GET Org B work definition
   814→User from Org A cannot GET Org B subcontract quote
   815→User from Org A cannot modify Org B estimate
   816→User from Org A cannot modify Org B work definition
   817→User from Org A cannot see Org B audit logs
   818→User from Org A cannot access Org B AI context
   819→```
   820→
   821→These tests are P0.
   822→
   823→Do not proceed until they pass.

   849→Do not silently rewrite environment variables.
   850→
   851→Document the Neon/Prisma connection strategy.
   852→
   853→---
   854→
   855→# 4. P0 — FIX UNSOURCED PRICE MATHEMATICS
   856→
   857→Current pricing behavior treats a missing price observation as:
   858→
   859→```text
   860→unsourced = true
   861→cost contribution = 0
   862→```
   863→
   864→This is unacceptable.
   865→
   866→A missing price is not zero cost.
   867→
   868→Implement:
   869→
   870→```ts
   871→calculationStatus:
   872→  | 'complete'
   873→  | 'incomplete'
   874→```
   875→
   876→or an equivalent typed state.
   877→
   878→If a mandatory recipe component has no valid price observation:
   879→
   880→```text
   881→calculationStatus = incomplete
   882→blockingInputs = [...]
   883→```
   884→
   885→The engine may return a provisional result for UI display, but it must NOT produce a commit-ready canonical price.
   886→
   887→Do not let:
   888→
   889→```text
   890→missing material price
   891→missing labour price
   892→missing equipment price
   893→```
   894→
   895→silently reduce estimated cost.
   896→
   897→The pre-submission gate must treat incomplete calculations as blockers.
   898→
   899→Add tests.
   900→
   901→Example:
   902→
   903→```text
   904→recipe:
   905→  cement = priced
   906→  sand = priced
   907→  mason = missing
   908→
   909→expected:
   910→  status = incomplete
   911→  blocking input = mason
   912→  canonical sellPrice cannot be finalized
   913→```
   914→
   915→---
   916→
   917→# 5. P0 — REMOVE THE 50% HYBRID SUBCONTRACT HEURISTIC
   918→
   919→The current pricing engine contains a heuristic equivalent to:
   920→
   921→```text
   922→hybrid =
   923→50% self-perform
   924→50% subcontract
   925→```
   926→
   927→This must be removed.
   928→
   929→The system must NEVER invent the split.
   930→
   931→Implement a structured hybrid allocation.
   932→
   933→For example:
   934→
   935→```ts
   936→interface ExecutionSegment {
   937→  strategy: 'self-perform' | 'subcontract'
   938→  scopeDefinition: string
   939→  quantity?: number
   940→  quantityPct?: number
   941→  costBasis: ...
   942→}
   943→```
   944→
   945→The exact model can follow project conventions.
   946→
   947→But:
   948→
   949→```text
   950→hybrid without an explicit split
   951→```
   952→
   953→must be:
   954→
   955→```text
   956→incomplete
   957→```
   958→
   959→not:
   960→
   961→```text
   962→50/50
   963→```
   964→
   965→If a subcontract quote exists, use it only against the scope explicitly assigned to the subcontractor.
   966→
   967→If the quote is incomplete, surface the uncovered scope.
   968→
   969→Add tests:
   970→
   971→```text
   972→70% self-perform / 30% subcontract
   973→100% subcontract
   974→100% self-perform
   975→hybrid with missing allocation
   976→hybrid with subcontract quote
   977→```
   978→

   981→# 6. P0 — FIX MARGIN SEMANTICS
   982→
   983→The current pricing engine calls:
   984→
   985→```ts
   986→(sellPrice - projectCost) / sellPrice
   987→```
   988→
   989→"margin", while `projectCost` is currently effectively direct cost.
   990→
   991→This is semantically incorrect for the commercial model we defined.
   992→
   993→Implement explicit financial concepts:
   994→
   995→```text
   996→directCost
   997→projectCost
   998→riskCost
   999→overheadCost
  1000→estimatedTotalCost
  1001→sellPrice
  1002→expectedProfit
  1003→expectedMargin
  1004→```
  1005→
  1006→At minimum:
  1007→
  1008→```text
  1009→estimatedTotalCost =
  1010→    directCost
  1011→    + project overhead
  1012→    + contingency/risk
  1013→```
  1014→
  1015→Then:
  1016→
  1017→```text
  1018→expectedProfit =
  1019→    sellPrice - estimatedTotalCost
  1020→```
  1021→
  1022→and:
  1023→
  1024→```text
  1025→expectedMargin =
  1026→    expectedProfit / sellPrice
  1027→```
  1028→
  1029→Use these terms consistently in:
  1030→
  1031→```text
  1032→engine
  1033→API
  1034→UI
  1035→provenance
  1036→adjudication
  1037→pre-submission gate
  1038→```
  1039→
  1040→Do not display "margin" when the number is actually markup/spread over direct cost.
  1041→
  1042→Add tests.
  1043→
  1044→---

  1046→# 7. P0 — REBUILD SUBCONTRACT SCOPE RECONCILIATION
  1047→
  1048→The current algorithm uses simple bidirectional substring matching and, when quote line detail is absent, treats the entire quote amount as scope coverage.
  1049→
  1050→That is insufficient.
  1051→
  1052→We explicitly designed subcontract reconciliation as a commercial protection mechanism.
  1053→
  1054→Do not fake semantic coverage with string matching.
  1055→
  1056→## New model
  1057→
  1058→Represent required scope as structured scope atoms.
  1059→
  1060→Example:
  1061→
  1062→```text
  1063→Aluminium Windows Package
  1064→
  1065→required scope:
  1066→  manufacturing
  1067→  delivery
  1068→  installation
  1069→  sealant
  1070→  scaffolding
  1071→  finishing
  1072→  testing
  1073→```
  1074→
  1075→A subcontract quote can cover each atom explicitly:
  1076→
  1077→```text
  1078→manufacturing      covered
  1079→delivery           covered
  1080→installation       excluded
  1081→sealant            excluded
  1082→scaffolding        unknown
  1083→finishing          covered
  1084→testing            not stated
  1085→```
  1086→
  1087→Coverage must be calculated from these structured assignments.
  1088→
  1089→AI may propose a mapping from supplier language to required scope atoms.
  1090→
  1091→But the mapping must be stored and reviewable.
  1092→
  1093→## Important
  1094→
  1095→Never treat:
  1096→
  1097→```text
  1098→lump-sum quote
  1099→```
  1100→
  1101→as:
  1102→
  1103→```text
  1104→100% scope coverage
  1105→```
  1106→
  1107→unless an explicit user or verified document analysis establishes that coverage.
  1108→
  1109→A lump-sum quote with no scope detail should be:
  1110→
  1111→```text
  1112→scopeCoverageStatus = unknown
  1113→```
  1114→
  1115→and should trigger review.
  1116→
  1117→## Required result
  1118→
  1119→For every selected subcontract quote show:
  1120→
  1121→```text
  1122→required scope
  1123→covered scope
  1124→excluded scope
  1125→unstated scope
  1126→assumptions
  1127→commercial exposure
  1128→```
  1129→
  1130→Add adversarial tests:
  1131→
  1132→```text
  1133→"Supply only" vs "supply and install"
  1134→"windows" vs "windows + installation"
  1135→"all works" with explicit exclusions
  1136→lump sum with no line breakdown
  1137→overlapping quote lines
  1138→duplicate quote lines
  1139→partial package
  1140→```
  1141→
  1142→---
