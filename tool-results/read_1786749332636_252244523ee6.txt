     1→     1→I checked the actual `pectoraux/contros` repository rather than trusting Z.ai's completion summary. My assessment is:
     2→     2→
     3→     3→**The implementation is a good visual/domain prototype, but it is not yet the architecture we froze, and I would not let Z.ai continue adding features until it fixes several P0 issues.**
     4→     4→
     5→     5→The most important problems are not cosmetic. They are **security/tenant isolation, estimate correctness, revision semantics, subcontract reconciliation correctness, and the fact that the current "completed" system is still a single Next.js prototype rather than the GenOffice-based product architecture we specified.**
     6→     6→
     7→     7→The repo is public and currently has 7 commits. Its schema does use PostgreSQL via `DATABASE_URL`/`DIRECT_DATABASE_URL`, so the Neon choice is now reflected in the code. ([GitHub][1])

    11→    11→There is real substance here.

    28→    28→
    29→    29→# P0 — The API is currently not enforcing tenant isolation
    30→    30→
    31→    31→This is the biggest issue I found.
    32→    32→
    33→    33→The database schema has `organizationId` on the major records and the auth implementation puts `organizationId` into the NextAuth JWT/session. ([GitHub][2])
    34→    34→
    35→    35→But the actual API routes are not consistently using that authenticated identity to scope queries.
    36→    36→
    37→    37→For example, the dashboard route simply does:
    38→    38→
    39→    39→```ts
    40→    40→db.opportunity.count(...)
    41→    41→db.subcontractPackage.count(...)
    42→    42→db.estimate.count(...)
    43→    43→db.knowledgeAlert.count(...)
    44→    44→db.auditLog.findMany(...)
    45→    45→db.opportunity.groupBy(...)
    46→    46→```
    47→    47→
    48→    48→with **no organization filter**. ([GitHub][7])
    49→    49→
    50→    50→The opportunities list likewise calls:
    51→    51→
    52→    52→```ts
    53→    53→db.opportunity.findMany(...)
    54→    54→```
    55→    55→
    56→    56→without an organization constraint. ([GitHub][8])
    57→    57→
    58→    58→That's incompatible with the architecture we froze:
    59→    59→
    60→    60→> Every organization must be isolated from every other organization.
    61→    61→
    62→    62→Having `organizationId` in the schema is not enough.
    63→    63→
    64→    64→### Required fix
    65→    65→
    66→    66→Create one mandatory server-side auth/context function, something like:
    67→    67→
    68→    68→```ts
    69→    69→requireAuth()
    70→    70→requireOrganization()
    71→    71→requireRole()
    72→    72→```
    73→    73→
    74→    74→and make every API route obtain:
    75→    75→
    76→    76→```ts
    77→    77→const ctx = await requireRequestContext()
    78→    78→
    79→    79→ctx.userId
    80→    80→ctx.organizationId
    81→    81→ctx.role
    82→    82→```
    83→    83→
    84→    84→Then every query must be scoped through server-derived `ctx.organizationId`.
    85→    85→
    86→    86→Even better, centralize repositories so application code cannot accidentally issue an unscoped query.
    87→    87→
    88→    88→For example:
    89→    89→
    90→    90→```ts
    91→    91→opportunityRepository.list(ctx, ...)
    92→    92→```
    93→    93→
    94→    94→rather than:
    95→    95→
    96→    96→```ts
    97→    97→db.opportunity.findMany(...)
    98→    98→```
    99→    99→
   100→   100→throughout the app.
   101→   101→
   102→   102→### Do not allow this pattern
   103→   103→
   104→   104→```ts
   105→   105→where: { id }
   106→   106→```
   107→   107→
   108→   108→for organization-owned entities.
   109→   109→
   110→   110→It must be:
   111→   111→
   112→   112→```ts
   113→   113→where: {
   114→   114→  id,
   115→   115→  organizationId: ctx.organizationId
   116→   116→}
   117→   117→```
   118→   118→
   119→   119→or, preferably, enforced at a repository/service boundary.
   120→   120→

   153→   153→
   154→   154→Validate them at startup.

   157→   157→
   158→   158→Do not rewrite environment variables in application code.

   160→   160→Also document the Prisma/Neon connection strategy clearly.

   164→   164→# P0 — The estimator can currently produce materially wrong costs
   165→   165→
   166→   166→This is more serious than a normal MVP approximation.
   167→   167→
   168→   168→The pricing engine explicitly says:
   169→   169→
   170→   170→> Missing price observation → unsourced, line contributes 0. ([GitHub][4])
   171→   171→
   172→   172→That means:
   173→   173→
   174→   174→```text
   175→   175→Cement
   176→   176→GHS 45
   177→   177→Sand
   178→   178→GHS 30
   179→   179→Labour
   180→   180→MISSING
   181→   181→```
   182→   182→
   183→   183→can produce a direct cost that silently excludes labour.
   184→   184→
   185→   185→The UI later flags the line as unsourced, but **the mathematical estimate is already wrong**.
   186→   186→
   187→   187→Our invariant was not:
   188→   188→
   189→   189→> "Flag bad estimates."
   190→   190→
   191→   191→It was:
   192→   192→
   193→   193→> **"Never let an unsupported number silently become the commercial truth."**
   194→   194→
   195→   195→### Correct behavior
   196→   196→
   197→   197→A missing mandatory price should produce:
   198→   198→
   199→   199→```text
   200→   200→calculationStatus = incomplete
   201→   201→```
   202→   202→
   203→   203→not:
   204→   204→
   205→   205→```text
   206→   206→cost contribution = 0
   207→   207→```
   208→   208→
   209→   209→The engine should return something like:
   210→   210→
   211→   211→```ts
   212→   212→{
   213→   213→  status: "incomplete",
   214→   214→  blockingInputs: [
   215→   215→    {
   216→   216→      kind: "missing-price",
   217→   217→      resourceId,
   218→   218→      resourceName
   219→   219→    }
   220→   220→  ]
   221→   221→}
   222→   222→```
   223→   223→
   224→   224→and should not produce a commit-ready `sellPrice`.
   225→   225→
   226→   226→The UI can still show a provisional estimate, but it must be explicitly provisional.
   227→   227→

   230→   230→# P0 — The hybrid subcontracting logic is an unacceptable heuristic
   231→   231→
   232→   232→This is probably the most concerning piece of the actual pricing engine.
   233→   233→
   234→   234→Z.ai has:
   235→   235→
   236→   236→```ts
   237→   237→// Heuristic: 50% of equivalent self-perform cost is subcontracted.
   238→   238→subcontractCost = subcontractFromRecipe + selfPerformTotal * 0.5;
   239→   239→```
   240→   240→
   241→   241→and:
   242→   242→
   243→   243→```ts
   244→   244→// The quote (if any) is ignored under this heuristic.
   245→   245→```
   246→   246→
   247→   247→([GitHub][4])
   248→   248→
   249→   249→That cannot exist in the commercial engine.
   250→   250→
   251→   251→We explicitly designed:
   252→   252→
   253→   253→```text
   254→   254→Self-perform
   255→   255→Subcontract
   256→   256→Hybrid
   257→   257→```
   258→   258→
   259→   259→as **real execution strategies**, not arbitrary assumptions.
   260→   260→
   261→   261→A 50/50 heuristic can materially distort a bid.
   262→   262→
   263→   263→### Required model
   264→   264→
   265→   265→Hybrid must define the actual split.
   266→   266→
   267→   267→For example:
   268→   268→
   269→   269→```text
   270→   270→WorkPackage
   271→   271→ ├── selfPerformComponents
   272→   272→ └── subcontractComponents
   273→   273→```
   274→   274→
   275→   275→or:
   276→   276→
   277→   277→```text
   278→   278→EstimateLine
   279→   279→ ├── executionSegments[]
   280→   280→ │     ├── strategy
   281→   281→ │     ├── scope
   282→   282→ │     ├── quantity
   283→   283→ │     └── cost basis
   284→   284→```
   285→   285→
   286→   286→Then:
   287→   287→
   288→   288→```text
   289→   289→70% self-perform
   290→   290→30% subcontract
   291→   291→```
   292→   292→
   293→   293→must actually mean 70/30, based on a structured allocation.
   294→   294→
   295→   295→If there is no allocation:
   296→   296→
   297→   297→> **The estimate is incomplete.**
   298→   298→
   299→   299→Never invent 50%.
   300→   300→

   303→   303→# P0 — The current "margin" is wrong
   304→   304→
   305→   305→This is subtle but important.
   306→   306→
   307→   307→The pricing engine calculates:
   308→   308→
   309→   309→```ts
   310→   310→marginPct = (sellPrice - projectCost) / sellPrice
   311→   311→```
   312→   312→
   313→   313→where `projectCost = directCost`. ([GitHub][4])
   314→   314→
   315→   315→But the actual sell price already includes:
   316→   316→
   317→   317→```text
   318→   318→risk
   319→   319→overhead
   320→   320→profit
   321→   321→```
   322→   322→
   323→   323→So this metric is not the actual profit margin.
   324→   324→
   325→   325→The API also exposes:
   326→   326→
   327→   327→```ts
   328→   328→averageMarginPct = (totalSell - totalDirect) / totalSell
   329→   329→```
   330→   330→
   331→   331→which has the same conceptual problem. ([GitHub][3])
   332→   332→
   333→   333→We need at least distinguish:
   334→   334→
   335→   335→```text
   336→   336→gross margin
   337→   337→contribution margin
   338→   338→operating margin
   339→   339→target profit margin
   340→   340→```
   341→   341→
   342→   342→For this MVP, the simplest correct model is:
   343→   343→
   344→   344→```text
   345→   345→direct cost
   346→   346→+ project overhead
   347→   347→+ contingency/risk
   348→   348→= estimated total cost
   349→   349→
   350→   350→sell price
   351→   351→- estimated total cost
   352→   352→= expected profit
   353→   353→
   354→   354→expected profit / sell price
   355→   355→= expected margin
   356→   356→```
   357→   357→
   358→   358→The UI must not label a cost-to-sell spread as "margin" if it includes no overhead/risk treatment.
   359→   359→

   362→   362→# P0 — The subcontract reconciliation algorithm is far too weak
   363→   363→
   364→   364→This is the biggest domain-model problem after pricing.
   365→   365→
   366→   366→The current matching algorithm is literally bidirectional substring matching:
   367→   367→
   368→   368→```ts
   369→   369→la.includes(lb) || lb.includes(la)
   370→   370→```
   371→   371→
   372→   372→and then matches the first unused quote line. ([GitHub][10])
   373→   373→
   374→   374→That is not sufficient for real subcontract packages.
   375→   375→
   376→   376→Example:
   377→   377→
   378→   378→```text Required:
   379→   379→Supply and install aluminum windows, 1,000m²
   380→   380→
   381→   381→Sub quote:
   382→   382→Aluminium windows
   383→   383→Supply only
   384→   384→```
   385→   385→
   386→   386→A textual match can report coverage even though **installation is absent**.
   387→   387→
   388→   388→Worse, if a subcontractor sends a lump-sum quote without line detail, the implementation says:
   389→   389→
   390→   390→> treat whole quote.totalAmount as coverage. ([GitHub][10])
   391→   391→
   392→   392→That defeats the entire purpose of scope reconciliation.
   393→   393→
   394→   394→### Correct architecture
   395→   395→
   396→   396→Reconciliation should be based on **scope atoms**, not descriptions.
   397→   397→
   398→   398→Example:
   399→   399→
   400→   400→```text
   401→   401→Package:
   402→   402→Aluminium windows
   403→   403→
   404→   404→Required scope atoms:
   405→   405→  manufacture
   406→   406→  delivery
   407→   407→  installation
   408→   408→  sealant
   409→   409→  scaffolding
   410→   410→  testing
   411→   411→  finishing
   412→   412→
   413→   413→Sub quote:
   414→   414→  manufacture ✓
   415→   415→  delivery ✓
   416→   416→  installation ✗
   417→   417→  sealant ✗
   418→   418→  scaffolding ✗
   419→   419→```
   420→   420→
   421→   421→Then coverage becomes semantic and auditable.
   422→   422→
   423→   423→AI can assist with mapping quote language to scope atoms, but the mapping must enter structured data and be reviewable.
   424→   424→

   434→   434→

   459→   459→
